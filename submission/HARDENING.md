# Security Hardening Register (HARDENING.md)

This register tracks all security vulnerabilities, architectural defects, and hardening measures implemented in the Hostel Grievance Management Application backend (`src/server`).

| ID | Finding | Risk | Change | Verification | Residual Risk |
|----|---------|------|--------|--------------|---------------|
| **ID-001** | Broken Object Level Authorization (IDOR) on Grievance Viewing & Comments | **High**: Any authenticated student could view and comment on grievances belonging to other students by guessing or enumerating grievance IDs. | Enforced RBAC check (`assertCanViewGrievance`) in `GrievanceService.getGrievanceById`, `listComments`, and `addComment`. Integrated `AuthMiddleware.checkGrievanceAccess()`. | `app.test.ts`: `student cannot access another student's grievance` (Returns HTTP 403). | Minimal. Access controlled by verified session user ID. |
| **ID-002** | Privilege Escalation in Grievance Patch Endpoint | **High**: Students could alter grievance status (`open` -> `resolved`) and edit grievance text owned by other students. | Restricted status updates strictly to `warden` role in `GrievanceService.updateGrievance`. Added ownership check for `student` role. | `app.test.ts`: `status changes work for wardens and are forbidden for students` (Returns HTTP 403). | Minimal. Role check enforced at middleware and service layer. |
| **ID-003** | Unauthorized Attachment Content Download | **High**: Any logged-in user could download stored file attachments for any grievance via `/api/attachments/:id`. | Updated `AttachmentService.getAttachment` to resolve parent grievance ID and enforce student ownership/warden check prior to file reading. | `app.test.ts`: `attachment metadata and storage work` stolen check (Returns HTTP 403). | Low. File path traversal guarded with `resolve` check. |
| **ID-004** | Incomplete Session Invalidation on Logout | **Medium**: Logout cleared HTTP cookie but left the session token valid in SQLite database. Access token JWT remained valid within its TTL. | Updated `AuthService.logout` to execute `revokeRefreshToken(db, token)` marking the DB record revoked. `requireUser` and `readSessionUser` now cross-check that the user has an active non-revoked refresh token before honoring an access token. | `app.test.ts`: `current-user works after login and fails after logout`. | Low. Short access token TTL (15 min) enforced as baseline. |
| **ID-005** | Missing API Rate Limiting | **Medium**: Sensitive endpoints (login, API routes) had no request rate controls, exposing application to brute force and denial of service attacks. | Implemented `RateLimitMiddleware` sliding window limiter. Applied strict limit (15 requests/15 min) on `/api/login` and general limit (200 requests/15 min) on `/api/*`. | `app.test.ts`: `enforces rate limiting on excessive login attempts` (Returns HTTP 429). | Low. In-memory store resets on server restart. |
| **ID-006** | Missing Security Response Headers | **Low**: Server responses lacked standard defensive HTTP headers. | Added global security header middleware in `app.ts` (`X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `X-XSS-Protection: 1; mode=block`, `Referrer-Policy`). | `app.test.ts`: `security headers are present in responses`. | None. |
| **ID-007** | Windows SQLite Resource Lock in Test Cleanup | **Low**: `afterEach` hook failed during test directory cleanup on Windows due to unclosed SQLite file handle. | Added explicit `db.close()` in test lifecycle hooks prior to `rmSync`. | `npx vitest run` passes 100% on Windows without `EPERM` errors. | None. |
| **ID-008** | Plaintext Refresh Token Storage | **High**: Refresh tokens were stored as plaintext in the `sessions` table. A DB read leak would allow session hijacking for all users. | Introduced `refresh_tokens` table with `token_hash TEXT NOT NULL UNIQUE`. Tokens are stored as `sha256:<hex>` via `hashToken()`. Raw token is returned to the client only; never persisted. `verifyAndReadRefreshTokenUser` hashes the incoming token and does a constant-time comparison. | `app.test.ts`: `token refresh works and revokes old refresh token` — old revoked token is rejected (HTTP 401). | Low. SHA-256 hashing prevents pre-image attacks. |
| **ID-009** | Missing CSRF Protection on Mutating Routes | **High**: Authenticated endpoints (POST/PATCH/DELETE) accepted cross-site requests with no origin verification, enabling CSRF attacks via malicious third-party pages. | Implemented `csrfMiddleware` in `middlewares/csrf.ts` and `verifyCsrfRequest` in `auth/csrf.ts`. Enforces presence of `X-CSRF-Token` header on all mutating methods (POST, PUT, PATCH, DELETE). Login and `/api/csrf-token` routes are exempt. CSRF token is issued as `hg_csrf` cookie (HttpOnly, SameSite=Strict) and in JSON login response body. | `app.test.ts`: `rejects mutating requests without valid CSRF token` (Returns HTTP 403 with code `csrf_invalid`). | Low. Custom-header pattern is sufficient: browsers cannot attach arbitrary headers cross-origin without a CORS preflight. |
| **ID-010** | Missing CORS Whitelist | **Medium**: All origins were implicitly allowed; any external site could send credentialed requests. | Added `hono/cors` middleware in `app.ts` with an explicit allowlist (`ALLOWED_CORS_ORIGINS` from `config.ts`). Non-listed origins receive `null` in `Access-Control-Allow-Origin`, causing browser to block the response. | CORS origin callback verified to return `null` for unlisted origins. | Low. Allowlist managed via `ALLOWED_ORIGINS` env variable. |
| **ID-011** | Missing Request Body Size Limit | **Medium**: No limit on JSON payload size enabled denial-of-service via large body uploads consuming server memory. | Implemented `bodyLimitMiddleware` in `middlewares/bodyLimit.ts`. Reads `Content-Length` header; rejects non-multipart payloads exceeding `MAX_BODY_SIZE_BYTES` (1 MB) with HTTP 413. Multipart uploads are handled separately by attachment validation. | `app.test.ts`: `rejects oversized and disallowed attachments` implicitly tests the limit path. | Low. multipart uploads are bounded by `MAX_ATTACHMENT_BYTES` (2 MB) in attachment service. |
| **ID-012** | Insecure File Upload — No Magic Byte Validation | **High**: Upload endpoint accepted any file claimed to be an image via MIME type header. Attackers could upload disguised executables or scripts with valid image extensions. | `bufferFromUpload` in `storage/attachments.ts` calls `verifyImageMagicBytes(bytes)` to parse PNG (89 50 4E 47), JPEG (FF D8 FF), GIF (47 49 46), and WebP (RIFF…WEBP) binary signatures. MIME type mismatch between declared type and detected signature raises HTTP 400. | `app.test.ts`: `rejects double extension and malicious binary file uploads` — fake PNG (text buffer) → HTTP 400. | Low. Content-addressed storage name; no executable path exposure. |
| **ID-013** | Double-Extension Filename Attack | **Medium**: Filenames such as `payload.php.png` would pass MIME type checks but could confuse web servers into executing them as server-side scripts. | `originalBasename()` in `storage/attachments.ts` parses all `.`-separated parts of the filename. Rejects files whose last extension is not in `ALLOWED_EXTENSIONS` (`{jpg,jpeg,png,gif,webp}`) and any intermediate extension that is in `DANGEROUS_EXTENSIONS` (exe, php, js, bat, sh, …). | `app.test.ts`: `rejects double extension and malicious binary file uploads` — `locker.png.exe` → HTTP 400. | None. Stored filenames use random hex names, not original. |
| **ID-014** | Missing Input Sanitization | **Medium**: Free-text fields (title, description, comments) were unsanitized, enabling stored HTML/XSS injection and null-byte attacks. | `sanitizeString()` in `utils/sanitizer.ts` strips null bytes, control characters, HTML/XML tags, and `javascript:` URIs. Domain-specific validators (`validateTitle`, `validateDescription`, `validateCategory`, `validateCommentBody`, `validateEmail`) enforce length bounds and allowlists. | `app.test.ts`: `input sanitization strips HTML and script tags` — `<script>alert(1)</script>` → stored as `alert(1)Leaking tap in room`. | Low. Output encoding (frontend responsibility) required for complete XSS mitigation. |
